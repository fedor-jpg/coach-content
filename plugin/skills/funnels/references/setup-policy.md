# Normal-MCP Setup Procedure

Local setup revision 1.1.0. Preparation is not configuration, installation or acceptance. This procedure takes precedence over historical native-policy/GraphQL recipes for ordinary MCP.

## Functional Gate

The selected detail's functional decision controls setup. Waiting for Chatfuel and source-incomplete/reference-only variants have no active plan: do not generate configuration payloads, offer activation, or fall back to the older 30 recipes. Keep source gaps separate from missing capabilities. Unconditional delivery cannot replace a verified-follow gate; ordinary DM cannot silently replace Story, Live, ad or referral entry. A different scenario requires an explicit new choice and is not completion of the blocked one.

Draft-available means only that the stated primary job has a concrete adaptation. It does not mean full reproduction. Keep omitted tracking/timers and acceptance gaps visible. Required email/phone must precede the gated URL, with all requested fields present; AI conversational checks are not deterministic validators or proof of saved values. Optional contact or SKIP can both lead to delivery where specified. Waitlist join/STOP replies are intent only until actual saved membership/withdrawal proof exists.

[Official Instagram messaging limits](https://chatfuel.com/docs/instagram/instagram-comment-autoreply#messaging-limits), checked 2026-11-02: a new commenter gets one private DM, then continuation waits for their actual reply. Existing contacts have a 24-hour window after their last message. Never prepare a second unsolicited comment DM. For an additional help message, preserve its content in the same approved link/coupon response after confirmation, or wait for a genuinely new user reply. Do not represent that as the original 60-second/two-minute timer. Generic silence followUps do not provide exact-delay or no-click behavior.

## Read And Prepare

1. Read the selected setup detail. Keep its complete source graph separate from the proposed adaptation. Preserve mandatory contact gates, alternatives, exact delays and external outcomes in the source assessment. Ask approval for each material change, not for an alleged equivalent import.
2. Ask only for missing business facts: account choice, offer, verified destination, selected post, goal-specific choices and consent purpose. When a source has comment and DM entries, ask which entry the owner wants; never enable both automatically. Draft the campaign name, entry word, complete messages and questions; infer language unless uncertain. Existing owner-supplied copy takes priority. Ask final approval, not an ASCII-name or message-writing questionnaire. Resolve IDs through available reads; never ask the user to copy IDs, transport text between chats, install a helper or run commands.
3. With authorized read access, use list_bots, get_bot and get_automation to identify the actual account, Main, scope bases, matching customs, switches, explicit/inherited settings and overlaps. Use list_posts with pagination when choosing posts. Without tools or access, still produce concrete draft copy/settings and name the unresolved read; do not invent account state.
4. Main need not be ON to discuss or prepare a draft. Do not enable it for setup or a test. Recheck current tool declarations and relevant get_playbook before any future write. The dated capability schema is evidence, not proof of current availability. After its review date, label operation readiness pending refresh. Source wording does not expire with capability evidence.
5. Show the complete proposed first message, actual continuation/alternative branches, required versus optional inputs, exact changed behavior, external steps and named blockers. Fill business placeholders from approved facts. A source URL, fixture, old email or inherited consent is not an approved current campaign value. Unknown editor variants do not block a known simpler adaptation if its own requirements are satisfied and the changes are approved.

## Approve And Configure Later

No writes are authorized by this library task. These steps describe a later, separately approved operation.

- For an existing owned OFF comment custom, record its complete baseline and explicit adoption approval. Before staging any setting, require complete readback equality with the approved post set, keyword set and match mode. Do not normalize away different words or modes. Missing or mismatched filters block staging even when the rule is OFF and owned. Reply-setting updates cannot alter filters. A mismatch requires a matching approved existing custom or separate immediate-enabled setup_comment_replies approval; never silently repair filters. If no suitable custom exists, normal MCP has no create-OFF command. Continue preparing copy; hold configuration. Never describe setup_comment_replies as a draft: it always enables, and creating a custom may turn Main ON and the comment base OFF. A later immediate-enabled setup needs a separate scoped yes covering exact posts/keywords/match mode/copy, overlap and those shared effects. A guide saying new customs start OFF is not an exposed normal command.
- For a comment-led continuation, prefer the owned comment custom. A general-DM fallback is a separate shared change, not automatic. DM-only adaptations use the actual DM base. An already ON base needs separate approval for live shared changes; an originally OFF base stays OFF during authorized staging. Do not silently change whenAIReplies schedules or replace unrelated support.
- Preserve the shared DM base's current whenAIReplies and followUps values, including inheritance, by default. Do not automatically write Always or DontSend. If the current schedule or active follow-ups conflict with the proposed campaign, identify the exact conflict and hold affected configuration. A base-wide change requires separate approval covering other campaigns and its full readback. Otherwise keep the existing settings and do not promise all-hours replies or campaign-only suppression. Owned comment settings remain separately scoped.
- Never bundle copy approval with shared-base settings approval. If current readback or an exact proposed settings diff is missing, hold configuration. Ask only the specific unresolved business choice, if any; otherwise state the missing readback or diff without an approval request. Do not ask blanket approval for "shared DM base changes". Any later shared-setting approval must be independent of copy approval and name the exact setting, current old value from readback, proposed new value, affected scope, inheritance change and effects on existing conversations or campaigns. Unknown old values cannot be invented. Copy approval never authorizes settings changes, activation or sends.

Append it to the fresh effective prompt, preserving all unrelated instructions. For an edit, replace only the exact unchanged owned block; duplicate or changed markers require reconciliation. Show the complete merged value and check its5000-character limit before approval. Without current readback, prepare the block only and hold the write. If the requested stop contract needs exact restoration, stop before writing; do not promise explicit values restore inheritance. setup_booking changes services/specialists; bookingRules changes Main autonomy globally. Neither is needed for an external booking URL.
- Keep an in-conversation journal of selected variant/revision, observed capability revision, account, exact IDs, original settings/inheritance/switches, approved diff, ownership and each readback. This is not hidden cross-chat storage. After each approved write, get_automation must confirm exact values and relevant switches before the next operation. Unknown write outcome means reconcile, not retry or switch executor.

## Preview, Edit, Return And Stop

- No sandbox or live test is part of preparation. test_reply saves a DM sandbox response and needs an active plan and Main already ON, even for an OFF rule. It is not continuing comment preview, recipient delivery or source routing proof. Never enable anything to unlock it in this scope. get_chat shows at most the last20 messages and may truncate; missing history is not zero leads or full lifecycle evidence.
- Refusal ends the current campaign before keyword matching. Do not reuse old consent/answers. A repeated same-run entry does not restart intake, duplicate capture or send an unsolicited reminder. One-shot comment plans keep silent terminal behavior; no invented refusal or clarification output. Distinct source alternatives remain alternatives, not a list of sequential sends.
- An edit changes only the approved diff. Re-read the account and affected settings, bind the new input/capability versions, invalidate old readbacks/previews, and obtain new approval for changed scope/copy. A capability refresh regenerates references only; it never edits existing campaigns.
- Return requires this conversation's journal plus current state. A new chat can prepare any library variant using business inputs. It cannot claim ownership or restore a previous chat's campaign without verified history. With missing journal, offer read-only reconciliation, not a duplicate or invented baseline.
- Stop: disable only the owned custom through set_automation_enabled(enabled:false); it cannot stop scope All/Main. A DM base may be disabled only if exclusively owned or separately authorized and unchanged. Otherwise remove only the exact owned campaign block/additions, preserving concurrent work. Read back every write. Stop is repeat-safe: an already verified OFF target needs no duplicate write. Sent messages and stored contact data are not erased.
- Restore explicit originals only where current prepared values and ownership still match. Exact inheritance restoration remains unresolved/dashboard-only. Never restore dormant Send follow-ups while a base stays ON. If restoration or ownership is uncertain, preserve unrelated work and report the exact deferred step. Settings OFF does not prove live silence.

## External Continuations And Evidence

Use the selected canonical continuation prompt only for the requested external outcome. Existing authorized providers come first. No automatic contact sync, signup, send, spend or installed bridge is implied. List membership can complete list growth; email/SMS sends are optional later outcomes. Native booking status does not prove external booking, registration or payment.

Report separately: source capture; documented tool primitive; prepared draft; configured/read back; sandbox; live delivery; full lifecycle acceptance. The accepted registry remains empty. Deterministic fixtures are not independent chats or Claude/Cowork tests.
