# Native execution brief

This is the maintainer procedure for the offline helper and exact-source release checks. The self-contained `chatgpt-funnels.md` is the direct-MCP runtime guide. Its named triage and Story-keyword variants do not change the literal-source statuses below. Reuse historical evidence only for its recorded revision and tested behavior; do not relabel a preview as current live acceptance.

## Prepare and configure

Use only the currently connected Chatfuel MCP. Read the relevant current playbook and schemas before native execution. The local helper uses the checked Public API shapes; it does not provide an API adapter or call a network. Mutations use `execute_mutation`, not `execute_query`. If the mutation executor or a required operation is absent, block that configuration path. Do not add a connector or substitute the immediately activating helper.

Read `get_bot`, `get_automation`, `get_knowledge_base`, actual posts, plan and inherited settings. With the Public API, use their documented query equivalents. The normalized local snapshot contains actual returned IDs, resolved settings and inheritance. It is not an invented remote schema. Verify the connected Instagram account, bot and complete rule list. A bot title containing an Instagram handle does not prove Instagram is connected. Read post IDs from the account, not user text. Detect overlapping post/keyword customs and shared DM instructions before writes.

New customs start OFF through `fuelyAutomationCreate`. `setup_comment_replies` turns the custom on immediately and disables the base; never use it for unfinished multi-step preparation. Keep the comment base and unrelated customs unchanged. Never assign a shared rule to this campaign because its name or keyword matches. Reuse only the card's owned ID with verified account, recipe, scope and current content fingerprint. If a compatible foreign rule overlaps, report the conflict rather than changing it.

Every `fuelyAutomationUpdateSetting` changes exactly one setting. Its wrapper is `{setting: {update: {...}}}`. Keep all required text fields nonempty, even inactive modes. Give new customs explicit replies, incoming behavior, follow-ups and handoff rather than relying on the base. For public-only thanks, set `privateReplyHowToReply: DontReply` and verify it on the OFF custom before enable. No Instagram arbitrary buttons, postbacks, deterministic AI graph or click timers are implied.

The first comment DM includes the promised value and at most one invitation. Wait for an actual inbound reply before asking the next question. An external link click is not an inbound reply. Test silence separately for new and existing contacts. Resolve follow-up inheritance and all other continuation sources, including the general DM base. Do not disable shared follow-ups silently. The helper blocks a shared follow-up conflict. AI needs a compatible active plan and credits; a plan alone does not enable a channel.

Read effective `whenAIReplies` for the general DM base and each owned AI continuation rule, including inheritance. Preparation, activation and enable require `option: Always`. `OutsideOfWorkingHours`, missing or unknown availability blocks these paths, including QR and direct-DM entry. The helper never changes schedules or this setting. Resolve restricted availability through separate readiness verification and explicit approval outside this preparation, then read native state again. A working-hours setting alone does not prove that AI can reply now.

DM recipes append one campaign-marked instruction block to the existing DM prompt; they do not create unsupported DM customs. Preserve all existing text and other campaign blocks. Recipe 6085 answers ordinary incoming support questions without a keyword. Other DM recipes use their declared entry word. Entry words are AI instructions, not deterministic filters. An ambiguous late "yes" must ask which campaign. Do not assign ordinary support to an unrelated campaign. Preserve existing ACTIVE handoff rules and captures when writing whole lists. For inactive lists, save their exact original values and inheritance in `ownership_before_write`; the campaign's enabled list contains only its own additions. Never activate foreign dormant entries. A capture uses `name`, not `attribute`; verify saved `validationErrors` before treating it as usable. No external subscription, phone call or waitlist membership follows from capture alone.

Show account, posts, messages, changes, recipients, shared effects and stop procedure. Obtain the real tool's yes/no approval. Save the exact plan, `ownership_before_write`, scoped intent and source snapshot in the private campaign card and verify storage before mutation. This record binds original values, dormant lists, inherited parent states, account, recipe and owned IDs before any setting write. After a create, read its OFF state and save its returned ID before preparing updates. Do not run symbolic or guessed IDs. Validate the complete plan before using any mutation payload.

For `shared_mode: off-staging`, `commands` configure the owned OFF custom and the originally OFF general DM base. Keep both OFF throughout. Shared settings remain inactive under that base, but preparation does not prove complete runtime isolation from every other source. Show all shared effects before staging. If the original OFF DM base has dormant follow-ups, stage `DontSend` and save the exact original state. Read back each setting. `verify --phase configure` checks the staged settings and original switches. `activation-plan` returns no shared writes for this branch. It does not enable anything.

For `shared_mode: live-activation`, `commands` configure only the owned OFF custom. `verify --phase configure` requires the originally ON DM base to remain unchanged. Run `activation-plan` against fresh readback. Obtain separate approval before its first shared write. Those writes affect live behavior immediately, one by one; the custom being OFF does not make shared writes inactive. Read each back before the next. Report partial activation or unknown results if a later step fails. Do not claim atomic writes or complete rollback.

For either branch, run `verify --phase activation`, then `enable-plan`. Obtain separate native approval for each enable and its shared effects. An originally OFF DM base has an explicit DM-enable command; the helper never places it among setting writes. Comment recipes additionally enable their owned custom. A DM-only recipe has no custom-enable command. Main must already be ON; preparing a campaign never enables Main, comment base, another custom or another channel. Run `verify --phase enabled` after approved enables. Tests finish with their originally OFF DM base and owned custom OFF. These checks are not Instagram delivery evidence.

For qualification, require this run's source and new explicit affirmative consent matching the presented opt-in in the approved language. Do not require an English consent token when the approved initial message presents a localized opt-in. Ask exactly the approved `question_one` and `question_two`, one at a time. Each needs a distinct subsequent actual inbound answer. The entry word and consent are not answers. Never reuse old answers, contact fields, summaries or prior consent. Do not add unrelated knowledge-base questions or offers. `next_step: handoff` hands the request to the team after those two answers. `next_step: booking_link` provides the existing destination when appropriate; completing two answers alone must not trigger handoff. Requests for a person, refusal or unresolved questions retain their approved handoff path. No link confirms a booking. These are AI instructions, not a deterministic event-state engine; verify the repeat and cross-campaign cases natively.

Substantive fields such as `bonus_text`, `thanks_text` and `consent_text` remain approved campaign facts; only the four exact message override fields are excluded from that facts section. Within an active campaign, missing price, availability, refund or other requested facts require native team handoff. A value marked unknown or not provided is not an answer. Resending a link or saying that no price was provided does not prove handoff. Do not repeat Main's greeting or restart the initial value on every reply. Preserve ordinary support outside the campaign.

Contact capture saves details for the team for the stated purpose. It does not send an email, schedule a call, subscribe a mailing list or complete another external action. Confirm only actual saved data. Do not promise an external delivery service that this recipe does not provide. Required email delivery or calling remains an unsupported requirement, not a new integration task.

Before waitlist preparation, read the complete account attribute namespace through `Bot.botAttributes`, not individual contact records. Include every platform and both system and custom attribute types, without name filters. Collect `edges.node.botAttribute.name`; follow `pageInfo.endCursor` with `after` until `hasNextPage` is false. Set normalized `known_attribute_names` to those names and `attribute_namespace_complete: true` only after all pages succeed. Missing or partial inventory blocks preparation and pre-activation checks. Also read capture names from every native rule, including disabled rules, dormant lists and inherited effective settings. At preparation, a membership name already present anywhere is a collision; choose a new launch-specific name rather than adopting it. The plan saves the complete original namespace in `ownership_before_write.attribute_namespace`.

Configuring an OFF rule can itself register its capture name globally, before any contact message or value. Re-read the namespace before activation and enable. A newly registered name is allowed only when saved complete inventory proves original absence and current campaign capture settings match the exact plan without inheritance. Foreign rules, including dormant lists, must still have no such name. Missing original proof or changed/duplicated owned captures blocks readiness. Do not omit new names from readback to pass this check. Stop only writes settings; native cleanup may remove an unused empty definition. Do not infer membership or its absence from a definition's presence. No contact attribute values are needed for the namespace check.

A stopped waitlist retains existing membership; an unused empty native definition may disappear after cleanup. Normal `prepare` still rejects an occupied name. For the same launch, use `restart-plan` with the ORIGINAL preparation, saved unchanged business inputs, latest stop plan, its `verify-stop` result and fresh complete native state. Keep the same campaign and attribute name whether its definition remains or disappears. The original plan must prove initial namespace absence. The stop plan must contain exact capture ownership observed before removal, with matching original campaign identity. Missing ownership proof cannot be repaired by inventing a receipt.

Restart requires a matching stop verification no older than 15 minutes and unchanged affected settings and switches. Unrelated rules and settings may change; the new plan preserves their current values. Changed purpose, name, scope, inputs, foreign captures, unknown actions or stale proof blocks restart. Read current namespace and rule settings again; never omit the existing attribute to pass a collision check. Save the restart plan and its fresh ownership before writes. It uses the same OFF staging or separately approved ON-DM activation and explicit enable steps as preparation. Repeating planning against the same state returns the same plan; changed staged state requires readback, not re-appending a campaign block.

On a late return, refresh the receipt with `verify-stop --plan SAVED_STOP --original-plan ORIGINAL --state FRESH`. This mode reuses the unchanged historical capture ownership and checks current affected settings, switches, scope and the full capture namespace. Unrelated additions or edits remain in current state. Save the new receipt for `restart-plan`; do not replace the saved stop with a new zero-command stop. A zero-command stop cannot reconstruct removed capture ownership. Missing or changed historical proof, a foreign capture or an affected change blocks refresh. Without `--original-plan`, `verify-stop` still requires complete exact readback.

Restart configures only settings. It does not delete, copy, reset or reenroll existing joined/withdrawn membership. Fresh source and consent remain required; old YES or a late answer cannot restart a stopped run. Keep the original preparation for later restart cycles, and use each cycle's latest stop and verification. `verify-stop` produces a bound check of supplied normalized readback, not proof of native provenance or live silence; Claude must obtain actual native reads. Missing or stale proof requires fresh readback and reconciliation, never a new campaign substitute.

## Return and uncertain actions

Restore the card through the campaign skill's verified private snapshot and Project locator procedure. Check every dependency and the current connected account. A local file or old successful restore does not prove portability to a new account. No manual file shuttling is part of the promised return path. If restoration is unavailable, allow read-only diagnosis, not a new duplicate setup.

Before each write/send, save intent with account, campaign, recipe digest, owned IDs, exact change and recipient if applicable. If a create/send response is lost, mark the result unknown. Read remote state/history and reconcile one unambiguous result. An absent result in one read is not a proven failure; do not retry unknown, pending or confirmed actions. A changed recipient, source, account, text, new answer or rule state invalidates relevant approval. Manual `send_chat_message` changes chat control; disclose that effect and require exact recipient/text approval. The helper prepares no sends.

Normal automatic messages use the current platform window from the last inbound contact message, not the last outbound message or Active status. Check the current playbook before applying any duration. The checked guide distinguishes the seven-day first comment reply from the normal 24-hour DM window; neither authorizes a delayed marketing sequence. Comment-context continuation and later general-DM fallback are separate live branches. A request for a person uses native handoff. `take_over_chat` may stop this AI conversation; it is not permanent opt-out across sources or reopening. A required permanent suppression guarantee blocks these recipes.

## Campaign leads

The coach returns to the Project and requests this campaign's leads; there are no notifications. Verify account before reading customer records. Page `contactChatsConnection`, then `Conversation.messages` with cursors. `list_chats` is candidate discovery, not campaign attribution. `get_chat`'s last 20 messages cannot prove completeness.

For comment recipes, use `InstagramInFeedCommentMessage` or `InstagramInReelCommentMessage`: `commentID`, `mediaContainer.id` and linked `privateReplyMessages`. Match approved media and actual initial DM, then the same recipient's inbound answers and handoff.

For keyword-based DM recipes, require an unambiguous campaign word and subsequent linked conversation, not timing alone. Exception: recipe `inro-6085` uses `entry_match: any_inbound`; no keyword is required. Link the actual ordinary inbound support event to its grounded answer or confirmed handoff. Verify the connected account, bot, recipient and contact-as-inbound actor against native history. Keep the source event and subsequent answer/handoff actors in the same verified recipient chain. Do not attribute unrelated campaigns, team-originated messages or timing alone to support.

Two campaigns in one chat require separate event chains. Missing, conflicting or truncated source evidence remains ambiguous, not zero leads.

Show only grounded campaign requests, actual answers and confirmed handoff. Use a chat link only when the current contract returned it. Store shown event IDs and cursors privately, not full chats. Mark updated answers as updates. Report partial pagination explicitly. Claim no new leads only after complete reading of the stated period. `attribute` checks a locally normalized event chain; native history and provenance still need live acceptance.

## Stop

Restore the exact saved preparation, including ownership saved before the first setting write. Read all campaign locations again. Run `stop-plan --plan PREPARED --state FRESH`. Save and read back the resulting stop intent before executing it. It disables an owned custom, removes only exact identifiable campaign additions and preserves concurrent text/list entries. An originally ON DM base stays ON. An originally OFF DM base returns OFF only when exact owned settings and unchanged other sources prove that disabling it will not affect concurrent work. Otherwise the helper leaves DM ON and reports its deferred `enabled` restoration while still returning safe owned-custom disable and campaign-removal commands. In this branch, preserve current shared modes: do not restore dormant follow-ups or turn off concurrent support. `restoration_complete` stays false. Main, other channels and unrelated rules remain unchanged. Modified or duplicated campaign additions are ambiguous; do not guess or overwrite them.

With exact current content and unchanged inheritance parents, restore original settings through `setInheritFrom` where the saved source inherited. For concurrent changes, retain explicit safe settings instead of reattaching changed parents. `deferred_restorations` reports this difference; it is not exact baseline restoration. Never restore dormant foreign entries into an active list. Stop may be repeated without adding new commands. An unknown native result still requires reconciliation, not a retry.

Read back every change and run `verify-stop --plan STOP --state FRESH`. Until then use "stopping" or "result unknown". Configuration-only evidence supports "settings stopped; live test pending", not complete stop. Store stopped-run identity privately. The helper does not add a tombstone to a restored original prompt or prove suppression after removal. Live tests must show that a new comment and late DM do not revive the offer, while a second campaign and ordinary support still work. A required stronger suppression guarantee remains blocked without native proof. Full silence for one person is a separate outcome with the handoff limits above. Local stop does not recall messages.

## Platform scope

These candidate recipes claim Instagram only. TikTok comment-to-DM is not equivalent: the public reply must ask the person to DM first, and AI needs its own plan. Facebook/TikTok are not eligible branches until explicitly designed and live-accepted. Story, Live, ad and QR candidates use ordinary incoming DMs and state the coach's placement step. They do not claim unsupported native triggers, ad attribution, QR scan attribution, random prizes, booking, payment or membership confirmation.

Recipe 6086 instead asks for automatic thanks after a story mention. Its status is unverified, not a claim that text acknowledgment is impossible. A StoryMention message type or missing reaction operation does not establish whether an automatic mention-triggered text reply works. Keep this recipe blocked and outside the customer catalogue until the actual trigger and automatic acknowledgment are verified; asking the person to DM first does not prove that goal.
